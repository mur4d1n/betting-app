# betting-app

Приложение реализует упрощённую схему взаимодействия между двумя сервисами: сервиса постинга некоторых событий и сервиса учёта ставок на эти события.

Запускается всё довольно просто:

```shell
docker-compose build
docker-compose up -d
```

Для работы приложения используется пять микросервисов:

  * `bet_maker`: микросервис, реализующий взаимодействие со ставками (создание, просмотр). Доступен по локалхосту на 8000 порте
  * `line_provider`: микросервис, реализующий взаимодействие с событиями (создание, изменение, просмотр). Доступен по локалхосту на 8080 порте
  * `redis`: используется в качестве шины сообщений, передаёт сообщения об окончании событий от `line_provider` к `bet_maker`
  * `postgres_bet_maker`, `postgres_line_provider`: два микросервиса с PostgreSQL на борту используются для постоянного хранения информации о ставках и событиях соответственно. Не самый лучший вариант для такого маленького задания, но я совершенно проглядел пункт о том, что в `line_provider` хранить события допускается и в памяти

## bet_maker

Реализует API для совершения и просмотра ставок. 

### Эндпоинты

#### POST /bet

Совершает ставку. Тело запроса должно иметь следующий вид:

```json
{
  "event_id": int,
  "bet_sum": Decimal
}
```

В ответе возвращается id совершённой ставки.

Если внутренний запрос к `line_provider` возвращает 404, выполнение запроса завершается с ошибкой с кодом 400.

Если внутренний запрос к `line_provider` возвращает любой другой код, не равный 200, выполнение запроса завершается с ошибкой с кодом 500.

Непредвиденные ошибки обрабатываются стандартно и возвращают код 500.

#### GET /bets

Возвращает список ставок в следующем формате:

```json
[
  {
    "id": int,
    "status": int
  },
  ...
]
```

  * Поле `id` содержит id ставки
  * Поле `status` содержит число, определяющее текуще состояние ставки. `-1` - событие ещё не завершилось, `0` - ставка не сыграла, `1` - ставка сыграла.

Непредвиденные ошибки обрабатываются стандартно и возвращают код 500.

#### GET /events

Возвращает список событий, на которые можно сделать ставку. Формат следующий:

```json
[
  {
    "id": int,
    "state": int,
    "coefficient": Decimal,
    "deadline": str
  },
  ...
]
```

  * Поле `id` содержит id события
  * Поле `state` содержит состояние события. Возможны три значения: `0` - событие ещё не завершилось, `1` - событие завершилось победой первой команды, `2` - событи езавершилось победой второй команды
  * Поле `coefficient` содержит текущий коэффициент ставки
  * Поле `deadline` содержит дедлайн для ставок - строку в формате `%Y-%m-%dT%H:%M:%S`

Непредвиденные ошибки обрабатываются стандартно и возвращают код 500.

## line_provider

### Эндпоинты

#### GET /event

Возвращает список событий, на которые можно сделать ставку. Формат следующий:

```json
[
  {
    "id": int,
    "state": int,
    "coefficient": Decimal,
    "deadline": str
  },
  ...
]
```

  * Поле `id` содержит id события
  * Поле `state` содержит состояние события. Возможны три значения: `0` - событие ещё не завершилось, `1` - событие завершилось победой первой команды, `2` - событи езавершилось победой второй команды
  * Поле `coefficient` содержит текущий коэффициент ставки
  * Поле `deadline` содержит дедлайн для ставок - строку в формате `%Y-%m-%dT%H:%M:%S`

Непредвиденные ошибки обрабатываются стандартно и возвращают код 500.

#### GET /event/{event_id}

Возвращает событие с указанным event_id (при наличии). Формат ответа:

```json
{
    "id": int,
    "state": int,
    "coefficient": Decimal,
    "deadline": str
}
```

  * Поле `id` содержит id события
  * Поле `state` содержит состояние события. Возможны три значения: `0` - событие ещё не завершилось, `1` - событие завершилось победой первой команды, `2` - событие завершилось победой второй команды
  * Поле `coefficient` содержит текущий коэффициент ставки
  * Поле `deadline` содержит дедлайн для ставок - строку в формате `%Y-%m-%dT%H:%M:%S`

При отсутствии в БД события с переданным event_id в ответе возвращается код 404.

Непредвиденные ошибки обрабатываются стандартно и возвращают код 500.

#### POST /event

Записывает в БД новое событие. Новые события записываются в БД со `state = 0` (`IN_PROGRESS`).

Тело запроса должно иметь следующий вид:

```json
{
  "event_id": int,
  "coefficient": Decimal,
  "deadline": str
}
```

  * Поле `event_id` содержит id события (в целом, мы могли бы его и просто автогенерить, но я совсем упустил это из виду)
  * Поле `coefficient` содержит начальный коэффициент ставки на событие. Коэффициент должен быть строго больше 1.00
  * Поле `deadline` содержит дедлайн для ставок - строку в формате `%Y-%m-%dT%H:%M:%S`

Непредвиденные ошибки обрабатываются стандартно и возвращают код 500.

#### PATCH /event/{event_id}

Обновляет существующее событие (при его наличии). В случае переведения state в 1 или 2 (`FIRST_WIN` и `SECOND_WIN` соответственно), порождает событие в Redis.

Тело запроса должно иметь следующий вид:

```json
{
  "state": Optional[int],
  "coefficient": Optional[Decimal],
  "deadline": Optional[str]
}
```

  * Поле `state` содержит новое состояние события. Возможны три значения: `0` - событие ещё не завершилось, `1` - событие завершилось победой первой команды, `2` - событие завершилось победой второй команды
  * Поле `coefficient` содержит новый коэффициент ставки на событие. Коэффициент должен быть строго больше 1.00
  * Поле `deadline` содержит новый дедлайн для ставок - строку в формате `%Y-%m-%dT%H:%M:%S` (не уверен, можно ли вообще сдвигать дедлайны у ставок, но пусть будет)

При отсутствии в БД события с переданным event_id в ответе возвращается код 404.

Непредвиденные ошибки обрабатываются стандартно и возвращают код 500.

## redis

Реализует шину событий через Redis Streams. Конфигурация совсем минимальная, без юзеров, авторизации и всего прочего.

Шина событий существует в потоке `events_stream`. Сообщения в нём имеют следующую структуру:

```
id: str
data: dict
timestamp: str (не используется, но может пригодиться в будущем)
```

Словарь `data` имеет следующий формат:

```json
{
  "event_id": int,
  "state": int
}
```

  * Поле `event_id` содержит id события
  * Поле `state` содержит новое состояние события. Возможны два значения: `1` - событие завершилось победой первой команды, `2` - событие завершилось победой второй команды

## postgres_bet_maker

Микросервис с СУБД PostgreSQL, используется для хранения сделанных ставок. БД содержит в себе одну таблицу: `bet`.

### Таблица `bet`

Таблица для хранения информации о ставках, имеет следующую структуру:

```sql
id INTEGER PRIMARY KEY AUTOINCREMENT
event_id INTEGER NOT NULL
sum NUMERIC(10, 2) NOT NULL
status betstatus NOT NULL -- IN_PROGRESS (-1), WIN (1), LOSE (0)
```

  * `id` - id ставки
  * `event_id` - id события, на которое сделана ставка
  * `sum` - сумма ставки
  * `status` - статус ставки

## postgres_line_provider

Микросеврис с СУБД PostgreSQL, используется для хранения событий. Бд содержит в себе одну таблицу `event`.

### Таблица `event`

Таблица для хранения информации о событиях, имеет следующую структуру:

```sql
id INTEGER PRIMARY KEY AUTOINCREMENT
state eventstate NOT NULL -- IN_PROGRESS (0), FIRST_WIN (1), SECOND_WIN (2)
coefficient NUMERIC(10, 2) NOT NULL
deadline DATETIME NOT NULL
```

  * `id` - id события
  * `state` - статус события
  * `coefficient` - коэффициент выигрыша
  * `deadline` - дедлайн для ставок
